# WiSP Server

HTTP backend that serves processed images to ESP32-based e-paper photo frames.

## Features

- Serves vendor-specific binary images to ESP32 firmware over HTTP
- Full image processing pipeline: EXIF rotation, aspect-ratio crop, brightness / contrast / gamma / hue / saturation / blur, dithering-based color reduction, timestamp overlay, and explicit rotation
- Floyd-Steinberg, Bayer, and Sierra3 dithering algorithms
- Multiple catalog providers: local filesystem, HTTP URL, and color-bar test pattern
- NDJSON streaming for large photo catalogs
- Concurrent image scanning using all available CPU cores
- SQLite (development), MySQL / MariaDB, and PostgreSQL database backends, switched via config
- Per-image visibility toggle via REST API
- Randomized image delivery with anti-repeat logic
- Bounded per-display delivery history: what was last handed to each frame, kept as a fixed-size ring

## Hardware Requirements

- A Waveshare e-paper display (see [Supported Display Models](#supported-display-models))
- ESP32 microcontroller running WiSP firmware
- Server host: Linux, macOS, or Docker (any platform that runs Go)

## Getting Started

> **Monorepo users:** to run the full stack (API + frontend together), start from the [repo root](../README.md) instead. The commands below work from within `api/` for API-only development.

### 1. First-time setup

```bash
make dev-setup
```

Creates `config/config.yaml` (SQLite, port 9002) and `config/service.yaml` and places sample photos in the configured source directory. Both files are gitignored.

### 2. Start the server

```bash
docker compose up
```

The API server starts on port 9002 with air hot-reload enabled.

### 3. Scan images into the database

```bash
docker compose exec api ./wisp catalog scan
# With verbose output:
docker compose exec api ./wisp catalog scan --verbose
```

### 4. Verify the server is running

```bash
curl http://localhost:9002/health
```

### Building locally (without Docker)

Prerequisites: Go 1.26+

```bash
make build
./wisp web run
```

### Testing

```bash
go test ./...
# With race detector:
go test -race ./...
# With HTML coverage report:
make test
```

### Linting

```bash
make lint-local
```

## Configuration

Both configuration files are gitignored and auto-generated by `make dev-setup`. Example files live in `config/`.

### `config/config.yaml`

```yaml
log_level: INFO        # DEBUG | INFO | WARN | ERROR
port: 9002
database:
  driver: sqlite       # sqlite | mysql | postgres
  dsn: /data/wisp.db
  log: false           # true logs every GORM query
  max_open_conns: 20   # connection pool ceiling for this process (default 20)
  max_idle_conns: 20   # connections kept between bursts (default 20)

delivery_history:      # see Delivery history below
  disabled: false      # negative on purpose — an absent `enabled:` would read as off
  size: 20             # deliveries kept per display (default 20, max 1000)
```

For MySQL or MariaDB, set `driver: mysql` and a DSN such as:

```
user:password@tcp(host:3306)/dbname?parseTime=true&charset=utf8mb4
```

For PostgreSQL, set `driver: postgres` and a DSN such as:

```
host=localhost port=5432 user=wisp password=password dbname=wisp sslmode=disable TimeZone=UTC
```

The URL form (`postgres://user:password@host:5432/dbname?sslmode=disable`) works too. Both
settings can also be supplied through the environment — `DB_DRIVER` and `DB_DSN` — and the
environment has the last word over the file. Set them together: a DSN written for one dialect
means nothing to another. To move an existing MySQL or MariaDB catalog to PostgreSQL, see
[Migrating from MySQL / MariaDB to PostgreSQL](docs/postgres-migration.md).

### `config/service.yaml`

```yaml
catalog:
  - key: photos
    type: file         # file | http | colorbar
    file:
      src_path: /mnt/wisp

displays:
  - name: my-frame
    mac_address: dev          # URL key → /pf/dev/image/random.bin
    model: ws7in3e            # see Supported Display Models
    orientation: landscape    # landscape | portrait
    flip: false
    show_timestamp: true
    color_reduction:
      type: floysteinberg     # floysteinberg | bayer | sierra3
      size: 4
      strength: 0.8
    catalog:
      - key: photos
    filters:                  # optional per-image adjustments
      - type: gamma
        properties:
          value: "1.2"
```

`mac_address` becomes the `:displayKey` path parameter. Use `dev` for local testing; set it to the ESP32 MAC address in production (the firmware sends requests to `/pf/{MAC}/image/random.bin`).

### Environment variables

Set on the API container — `environment:` in [`compose.yaml`](../compose.yaml). All are optional.
Where a variable overrides a `config.yaml` setting, the variable wins; one that is set but empty
counts as unset and leaves the file's value alone.

| Variable | Default | Effect |
|----------|---------|--------|
| `ALLOWED_ORIGINS` | `*` — every origin | Comma-separated list of origins allowed to make cross-origin requests. See [Access control](#access-control) |
| `DB_DRIVER` | `database.driver` from `config.yaml` | Overrides the driver (`sqlite`, `mysql` or `postgres`); an unknown name is refused at startup. Set it with `DB_DSN` |
| `DB_DSN` | `database.dsn` from `config.yaml` | Overrides the DSN, so credentials need not be written to a file |
| `DB_MAX_OPEN_CONNS` | `database.max_open_conns`, default `20` | Connection pool ceiling for this process. See [Connection pool](#connection-pool) |
| `DB_MAX_IDLE_CONNS` | `database.max_idle_conns`, default `20` | Connections kept open between bursts |
| `DB_DEFAULT_DSN` | — | Deprecated former name of `DB_DSN`. Still read, and logs a warning; `DB_DSN` wins where both are set |
| `WISP_AUTO_MIGRATE` | unset | `1` runs AutoMigrate on startup — needed once after a schema change, see [Delivery history](#delivery-history) |
| `WISP_SCAN_CONCURRENCY` | `min(GOMAXPROCS, 4)` | Images decoded in parallel by `catalog scan`. Lower it on a memory-constrained host |
| `ENV` | unset | Recorded as `env` on the server's log lines; changes no behaviour |

### Connection pool

`database/sql` opens as many connections as there are concurrent requests unless it is given a
ceiling, and one photo grid asks for a few hundred thumbnails at once. Against MySQL that was
survivable: a connection there is a thread and the server's own limit is high. PostgreSQL forks
a process per connection and ships with a much lower ceiling — the shipped default is 100 — so
the same burst reaches it and the server answers `sorry, too many clients already`. Every
request in the burst fails, which reads in the browser as thumbnails that will not load.

The pool bounds this: past `max_open_conns`, a request waits for a connection to come free
instead of opening another. The burst arrives as latency rather than as errors, and since the
queries behind it are primary-key lookups of at most a thumbnail's worth of bytes, the queue
drains quickly.

Set it below the database's own limit, and remember the limit is shared: a deployment runs the
web server and whichever scheduled command is due at the same time, each with its own pool. Use
`DB_MAX_OPEN_CONNS` to give a `catalog scan` a smaller share than the server, since they run
from the same image and the same `config.yaml`.

### Access control

There is none. No endpoint on this server is authenticated — not the management API, not the device API — so anything that can reach the port can list catalogs, read thumbnails, change image visibility, and read the delivery history. Run it on a trusted LAN, and put a reverse proxy that authenticates in front of it if it has to be reachable from anywhere else.

`ALLOWED_ORIGINS` is not a substitute for that. It defaults to `*` because the shipped compose setup serves the frontend on port 8080 and the API on 9002 — cross-origin — so a restrictive default would break the standard deployment. CORS governs only what a browser on someone else's page may read back; it stops no direct request. Set it to the frontend's origin regardless in any deployment where the API is reachable beyond a trusted network:

```
ALLOWED_ORIGINS=https://photos.example.com
```

## Upgrading

### `thumb_jpg` widens to `longblob` — MySQL and MariaDB only

Adding PostgreSQL support removed the MySQL-specific column types from the models, because
those type names are not valid PostgreSQL. One column changes width as a result, and the
first `AutoMigrate` after the upgrade emits a single statement:

```sql
ALTER TABLE `images` MODIFY COLUMN `thumb_jpg` longblob NOT NULL
```

This widens the column from 64 KB to 4 GB. It cannot lose data, it runs only for
installations that set `WISP_AUTO_MIGRATE=1`, and it is idempotent — later runs emit nothing.

MySQL cannot make the change in place (`ERROR 1846: ALGORITHM=INPLACE is not supported`), so
the table is copied once and **writes to `images` block until the copy finishes** — minutes
on a multi-gigabyte catalog. Schedule it for a quiet moment, and take a dump first:

```bash
mysqldump --single-transaction wisp > wisp-before-upgrade.sql
```

SQLite already rebuilds its tables on every `AutoMigrate`, so it does no extra work.
PostgreSQL has no installed base and is unaffected.

## API Reference

Base URL: `http://localhost:9002`

| Method | Path | Description |
|--------|------|-------------|
| GET | `/health` | Liveness probe |
| GET | `/version` | Build version and commit hash |
| GET | `/api/catalogs` | List all configured catalogs |
| GET | `/api/catalog/:catalogKey/images` | NDJSON stream of images in catalog |
| GET | `/api/catalog/:catalogKey/image/:imgid` | Single image thumbnail by ID |
| POST | `/api/catalog/selected/_toggle-visibility` | Toggle show/hide for a list of image IDs |
| GET | `/api/devices` | Every configured display, with what was last delivered to it |
| GET | `/api/device/:displayKey/deliveries` | Recent deliveries for one display, newest first (`?limit=` clamped to the ring size) |
| GET | `/pf/:displayKey/image/random.bin` | Random image for ESP32 (vendor binary) |
| GET | `/pf/:displayKey/image/random.jpg` | Random image for ESP32 (JPEG) |

## Usage

### CLI commands

```bash
./wisp web run                    # Start API server (default port 9002)
./wisp catalog scan               # Index images from all configured providers
./wisp catalog scan --verbose     # Index images with per-file logging
./wisp catalog purge-orphans      # Remove DB records with no matching source file
./wisp catalog list               # List all catalogs
./wisp catalog list-images        # List images in default catalog
./wisp system prune               # Drop and recreate the Image table
./wisp version                    # Show build version and commit hash
```

### Catalog providers

| `type` | Description |
|--------|-------------|
| `file` | Scans a local directory for JPEG, PNG, GIF, BMP, HEIF, TIFF, and WebP files |
| `http` | Fetches images from an HTTP URL |
| `colorbar` | Generates a color-bar test pattern (useful for display tuning) |

### Image processing pipeline

Each image served to an ESP32 passes through these steps in order:

1. EXIF rotation correction
2. Aspect-ratio crop to display dimensions
3. Configurable filters: brightness, contrast, gamma, hue, saturation, blur
4. Color reduction with dithering (Floyd-Steinberg, Bayer, or Sierra3)
5. Timestamp overlay (optional — controlled by `show_timestamp`)
6. Explicit rotation (optional)

### Delivery history

The server keeps a bounded record of the pictures it has handed to each display, so an operator can tell whether a frame on a wall is still being fed. `GET /api/devices` lists every configured display with a summary of its history; `GET /api/device/{display key}/deliveries` returns one display's recent entries, newest first.

Delivered means handed over, and nothing more. A record is written after the response body has gone out, and nothing can be added to it afterwards, so the server knows only that it wrote the bytes — not that the panel was awake to receive them, that it rendered them, or that it still holds that picture. A frame may be offline, flat, or stuck on last week's photograph and the history will look exactly the same. It is deliberately not a "last seen" either: the server saw a request, and only the response proves a delivery.

Each record holds when the picture went out, what kind it was (`photo`, `http`, `colorbar` or `error`), the image and catalog it came from where there was one, and the sleep interval the server asked the panel for in `X-Sleep-Seconds` — what was requested, not an interval the device is known to have kept. An `error` entry also carries a reason code: `no_images`, `db_error`, `file_missing`, `no_catalog`, `no_provider`, `unknown_display`, `load_failed` or `encode_failed`.

An `error` entry does not mean the request failed. The file provider gives up quietly — an empty catalog, an unreachable database, a file that has left the disk — and sends a rendered error card with an ordinary HTTP 200. Those are recorded as errors precisely because an error card, and not a photograph, is what the frame was handed — which makes them the thing worth watching for.

A display that has never been delivered to is still listed by `/api/devices`, with a null `last_delivered_at` and zero counts. That is deliberate: a frame that has never come to fetch is the most valuable thing this reports, and it must not be mistaken for one the server forgot to list.

Only displays named in `config/service.yaml` are recorded. The device API is unauthenticated, so the display key is whatever the requester put in the path; recording every MAC address that turned up would let anything on the network create rows at will.

The history is bounded, not trimmed. Each display holds at most `delivery_history.size` rows (default 20, max 1000), overwritten in place as new deliveries arrive, so the table cannot grow with time — its size is set by the configuration and the number of displays, not by how long the installation has been running. The per-display counts therefore cover only the entries still held and are not lifetime totals. Raising the size needs nothing. Lowering it leaves the rows above the new end where they are until the next server start, which deletes them, along with the history of any display that has since left `service.yaml`.

Setting `disabled: true` stops new deliveries being written down; it does not delete what is already stored, and `/api/devices` reports `recording_enabled: false` so a client can say that the counts have stopped moving rather than the frames.

> **Upgrading an existing installation:** the history table is created by AutoMigrate, which only runs when `WISP_AUTO_MIGRATE=1` is in the server's environment, and it is off by default: uncomment the line in the repo root [`compose.yaml`](../compose.yaml), or add it to `environment:` in `api/compose.yaml`. Recording is designed to fail quietly, because a history that cannot be written must never cost a panel its picture, so until the table exists the symptom is an empty history and a warning in the log rather than an error. Set it, restart once, and entries start appearing from the next delivery.
