# Migrating from MySQL / MariaDB to PostgreSQL

WiSP supports `sqlite`, `mysql` and `postgres` as `database.driver`. This guide covers
moving an existing MySQL or MariaDB catalog to PostgreSQL.

There are two routes:

| Route | Effort | Data kept |
|--------|--------|-----------|
| [Copy the data with pgloader](#route-1--copy-the-data-with-pgloader) | Higher — one external tool, a few manual steps | Everything |
| [Rebuild by re-scanning](#route-2--rebuild-by-re-scanning) | Lower — two commands | Only what the filesystem can reproduce ([details](#what-a-re-scan-cannot-reproduce)) |

Take route 1 if you have hidden any photos in the UI, have run `catalog tagging run`, or
use HTTP catalogs. Take route 2 if your catalogs are plain `file` providers that you have
never customised from the UI.

> **Back up first.** Both routes are one-way. Take a `mysqldump` of the source database
> before you start, and keep it until the new database has served images for a few days.

## Prerequisites

- PostgreSQL 11 or newer (the verification queries use the built-in `sha256()`)
- An empty database and a role that owns it
- For route 1: [pgloader](https://pgloader.readthedocs.io/) 3.6 or newer

The PostgreSQL DSN goes in `config/config.yaml`. The driver name is `postgres`:

```yaml
database:
  driver: postgres
  dsn: "host=127.0.0.1 port=5432 user=wisp password=wisp dbname=wisp sslmode=disable TimeZone=UTC"
```

The URL form (`postgres://wisp:password@127.0.0.1:5432/wisp?sslmode=disable`) works too.

The DSN can also be supplied through the `DB_DEFAULT_DSN` environment variable, which
overrides the file.

## Schema differences

WiSP does not ship SQL migrations — the schema is generated by GORM `AutoMigrate` from the
models in `app/domain/model/`. The two dialects therefore produce different DDL for the same
model.

### `images`

| Column | MySQL / MariaDB | PostgreSQL |
|--------|-----------------|------------|
| `id` | `bigint unsigned AUTO_INCREMENT` | `bigserial` |
| `catalog_key` | `varchar(64) NOT NULL` | `varchar(64) NOT NULL` |
| `rnd` | `double NOT NULL` | `double precision NOT NULL` |
| `src` | `varchar(2048) NOT NULL` | `varchar(2048) NOT NULL` |
| `src_hash` | `char(40) NOT NULL` | `char(40) NOT NULL` |
| `src_type` | `varchar(16) NOT NULL DEFAULT 'file'` | `varchar(16) NOT NULL DEFAULT 'file'` |
| `taken_at` | `datetime(3) NULL` | `timestamptz` |
| `image_orientation` | `bigint` | `bigint` |
| `thumb_jpg` | `longblob NOT NULL` | `bytea NOT NULL` |
| `image_data` | `longblob` | `bytea` |
| `excluded` | `tinyint(1) NOT NULL DEFAULT false` | `boolean NOT NULL DEFAULT false` |
| `file_modified_at` | `datetime(3) NULL` | `timestamptz` |
| `deleted_at` | `datetime(3) NULL` | `timestamptz` |
| `created_at` | `datetime(3) NOT NULL` | `timestamptz NOT NULL` |
| `updated_at` | `datetime(3) NOT NULL` | `timestamptz NOT NULL` |

Notes:

- Databases created before PostgreSQL support have `thumb_jpg blob` rather than `longblob`.
  The models used to pin `blob` and `longblob` explicitly and no longer do, because those
  type names are not valid PostgreSQL. Either width is copied correctly by the rules below,
  and `rnd` is unaffected — it is declared as standard-SQL `double precision`, which every
  backend accepts. Note that
  upgrading such an installation rewrites the `images` table once and blocks writes while it
  does — see [Upgrading](../README.md#upgrading) before you start.
- `image_orientation` is a Go `int`, which is 64-bit, so both dialects get a 64-bit column
  even though the stored values are 0, 1 or 2.
- `char(40)` becomes `bpchar(40)` in PostgreSQL, which blank-pads short values. `src_hash`
  is always a 40-character SHA-1 hex digest, so nothing is ever padded.
- PostgreSQL has no unsigned integers. `id` widens from `bigint unsigned` to signed
  `bigint`; the ceiling drops from 2^64 to 2^63, which no catalog will reach.
- `thumb_jpg` is capped at 60000 bytes by the encoder (`app/usecase/thumbnail.go`),
  well inside both column types.

### `tags` and `image_tags`

| Table | Column | MySQL / MariaDB | PostgreSQL |
|-------|--------|-----------------|------------|
| `tags` | `id` | `bigint unsigned AUTO_INCREMENT` | `bigserial` |
| `tags` | `name_normalized` | `varchar(128) NOT NULL` | `varchar(128) NOT NULL` |
| `tags` | `display_name` | `varchar(128) NOT NULL` | `varchar(128) NOT NULL` |
| `tags` | `created_at`, `updated_at` | `datetime(3) NOT NULL` | `timestamptz NOT NULL` |
| `image_tags` | `image_id`, `tag_id` | `bigint unsigned` | `bigint` |
| `image_tags` | `created_at` | `datetime(3) NOT NULL` | `timestamptz NOT NULL` |

### Indexes

Index definitions are dialect-independent — the same set is created on both:

| Table | Index | Columns |
|-------|-------|---------|
| `images` | `idx_random` | `catalog_key`, `image_orientation`, `deleted_at`, `excluded`, `rnd` |
| `images` | `idx_list_catalog` | `catalog_key`, `excluded`, `taken_at`, `deleted_at` |
| `images` | `idx_list_all` | `deleted_at`, `taken_at` |
| `images` | `idx_catalog_src` (unique) | `catalog_key`, `src_hash` |
| `tags` | `idx_tags_name_normalized` (unique) | `name_normalized` |
| `image_tags` | `idx_tag_lookup` | `tag_id`, `image_id` |

WiSP uses `deleted_at` for soft deletes, but it is not a GORM convention here: `excluded`
marks entries excluded by catalog configuration, while `deleted_at` records photos the user
hid from the UI. A scan never writes `deleted_at`.

### Undated photos change position in the grid

Expect this one — it is visible immediately after the migration and looks worse than it is.

PostgreSQL sorts `NULL` as larger than any value; MySQL, MariaDB and SQLite sort it as
smaller. `ListByCatalog` (`app/infra/repository/image.go`) orders by `taken_at desc`, and it
backs `GET /api/catalog/:catalogKey/images` and therefore the photo grid in the SPA, so
photos with no `taken_at` move from the end of the grid to the front:

```
MySQL / MariaDB   2021-01-01 | 2020-01-01 | (null)
PostgreSQL        (null)     | 2021-01-01 | 2020-01-01
```

`taken_at` is NULL whenever the source file carried no EXIF date — common for scans,
screenshots, and photos put through an export pipeline that strips metadata. This is the
engines' standard NULL ordering rather than anything WiSP decides; no data is affected, and
the dated photos keep their order relative to one another. A catalog whose photos all carry
EXIF dates looks identical before and after.

## Route 1 — copy the data with pgloader

The schema is created by WiSP, not by pgloader. That guarantees the result is exactly what
`AutoMigrate` expects, including index names, and reduces pgloader's job to moving rows.

### 1. Create the empty schema

Point `config/config.yaml` at the new PostgreSQL database, then run any command with
`WISP_AUTO_MIGRATE=1`. Every subcommand opens the database at startup, so `version` is
enough:

```bash
WISP_AUTO_MIGRATE=1 ./wisp version
```

Confirm the three tables exist and are empty:

```sql
\dt
SELECT count(*) FROM images;
```

### 2. Load the data

Save this as `wisp-migration.load`:

```
LOAD DATABASE
     FROM     mysql://wisp:password@mariadb-host/wisp
     INTO     postgresql://wisp:password@postgres-host/wisp

 WITH data only, truncate

 SET TimeZone to 'Asia/Tokyo'

 CAST type datetime  to timestamptz using zero-dates-to-null,
      type timestamp to timestamptz using zero-dates-to-null,
      type tinyint when (= 1 precision) to boolean using tinyint-to-boolean,
      type blob     to bytea using byte-vector-to-bytea,
      type longblob to bytea using byte-vector-to-bytea

 INCLUDING ONLY TABLE NAMES MATCHING 'images', 'tags', 'image_tags'

 ALTER SCHEMA 'wisp' RENAME TO 'public';
```

The `CAST` rules are stated explicitly rather than left to pgloader's defaults, so the result
does not depend on the pgloader version:

- `zero-dates-to-null` turns MySQL's `0000-00-00 00:00:00` into `NULL`. PostgreSQL rejects it
  outright, so without this rule the load fails on any row that has one.
- `tinyint-to-boolean` maps `excluded` back to a real `boolean`. MariaDB stores GORM's
  `boolean` as `tinyint(1)`.
- `byte-vector-to-bytea` covers `thumb_jpg` (`blob`) and `image_data` (`longblob`).

`ALTER SCHEMA 'wisp' RENAME TO 'public'` is required because pgloader otherwise targets a
PostgreSQL schema named after the source MySQL database. Replace `wisp` with your MySQL
database name.

**Time zones.** MySQL `datetime` has no zone. The values were written by the API in whatever
zone the MySQL DSN's `loc=` parameter named — the example config uses `loc=Local`, which is
the API container's `TZ` (`Asia/Tokyo` in the shipped compose files). `SET TimeZone` tells
PostgreSQL how to interpret those naive values on the way into `timestamptz`; set it to that
same zone or every timestamp shifts.

Check the plan, then run it:

```bash
pgloader --dry-run wisp-migration.load
pgloader wisp-migration.load
```

### 3. Reset the sequences

A data-only load writes the `id` values straight in and leaves the `bigserial` sequences at
their starting value, so the next insert would collide. Reset both:

```sql
SELECT setval(pg_get_serial_sequence('images', 'id'), COALESCE(max(id), 0) + 1, false) FROM images;
SELECT setval(pg_get_serial_sequence('tags',   'id'), COALESCE(max(id), 0) + 1, false) FROM tags;
```

`image_tags` has a composite primary key and no sequence.

### 4. Start WiSP

Leave `WISP_AUTO_MIGRATE` unset from now on, then go to [Verifying the migration](#verifying-the-migration).

## Route 2 — rebuild by re-scanning

Point `config/config.yaml` at the new database, then create the schema and re-index in one
step:

```bash
WISP_AUTO_MIGRATE=1 ./wisp catalog scan
```

This re-reads and re-thumbnails every photo, so it takes about as long as the original scan
did — hours for a large catalog.

### What a re-scan cannot reproduce

A scan writes `catalog_key`, `src`, `src_hash`, `taken_at`, `image_orientation`, `thumb_jpg`,
`file_modified_at` and `excluded`. Everything below is lost:

| Lost | Where it lived | Can it be rebuilt? |
|------|----------------|--------------------|
| Photos you hid in the UI | `images.deleted_at` | No. Written only by the visibility toggle (`POST /catalog/selected/_toggle-visibility`), and a scan deliberately never touches the column. Every hidden photo comes back visible. |
| All tags | `tags`, `image_tags` | Only by re-running `catalog tagging run`. That costs another full pass of LLM calls and will not return identical tags. |
| HTTP catalog images | rows with `src_type = 'http'`, including `images.image_data` | No. `catalog scan` only walks `file` providers. The image bytes live in `image_data` and nowhere else — there is no file on disk. `catalog fetch` refills the cache with *new* images from the endpoint, not the ones you had. |
| Image IDs | `images.id` | No — rows are renumbered from 1. Only matters if `service.yaml` pins one with `http.image_source.mode: fixed` and an `image_id`; that ID must be looked up again. |
| Row age | `images.created_at` | No — reset to the scan time. It is the FIFO eviction order for HTTP catalog caches, which are lost anyway. |

`excluded` is re-derived from the catalog `criteria` in `service.yaml`, so it survives as long
as that configuration is unchanged. `rnd` is regenerated and evened out at the end of every
scan and carries no meaning worth preserving.

## Verifying the migration

Compare row counts between the old and new databases. The same query runs on both:

```sql
SELECT count(*) FROM images;
SELECT count(*) FROM tags;
SELECT count(*) FROM image_tags;
SELECT count(*) FROM images WHERE deleted_at IS NOT NULL;
SELECT count(*) FROM images WHERE excluded;
```

Check that the binary columns survived the `bytea` conversion byte for byte. Total sizes
should match exactly:

```sql
-- both dialects
SELECT sum(length(thumb_jpg)), sum(length(image_data)) FROM images;
```

Then spot-check a few individual rows. Pick IDs that have both a thumbnail and image data,
and compare the digests:

```sql
-- MariaDB
SELECT id, sha2(thumb_jpg, 256) FROM images WHERE id IN (1, 2, 3);

-- PostgreSQL
SELECT id, encode(sha256(thumb_jpg), 'hex') FROM images WHERE id IN (1, 2, 3);
```

Both return lowercase hex; they must be identical.

Finally, confirm the service works end to end:

```bash
curl -f http://localhost:9002/health
curl -sI http://localhost:9002/pf/dev/image/random.bin
```

The second call should return `200` with an `X-Sleep-Seconds` header. Repeat it a few times —
it exercises `idx_random` and writes `rnd` back, which is the one query path that touches
every column type at once.

## Rolling back

Nothing in either route writes to the source database. To go back, restore `database.driver`
and `database.dsn` in `config/config.yaml` to the MySQL values and restart. Anything added
to the PostgreSQL database after the cutover stays there.
