# WiSP 長期運用構造レビュー — 10年レンズ

- **対象**: `wisp/` モノレポ(`api/` Go バックエンド、`frontend/` Vue SPA、`firmware/` ESP32)
- **前提**: 本システムを今後10年以上、実質1人で自宅セルフホスト運用する
- **実施日**: 2026-07-06
- **方法**: 4系統(バックエンド / フロントエンド / ファームウェア / 運用・横断)の並行コード監査。クリティカル判定は本文記載のファイル・行を直接再検証済み

---

## 総評

**骨格は10年もつ。リスクは分散しておらず、数カ所に集中している。**

ヘキサゴナルなバックエンド、レイヤリングの効いたフロントエンド、タイムアウト規律の徹底したファームウェア、商用リポジトリ以上のCI——個々の作りは趣味プロジェクトの水準を大きく超えている。一方で10年運用を脅かすのは「散らかり」ではなく、次の4点に集約される構造的リスクである。

1. **配備済みデバイスを直す手段がない**(OTA不在)——ハードウェアを持つプロジェクトで最も時間に効く負債
2. **リポジトリ単体からシステムを再現できない**(設定テンプレートの旧名残り、`make scan` 不在、動く設定は gitignore 下にのみ存在)
3. **システムが生み出したデータに複製が1つもない**(バックアップ皆無、WAL ホットコピー罠つき)
4. **画面描画の心臓部が、保守放棄された beta 版ライブラリの非公開APIに依存**している

いずれも「今日は正常に動く」ため表面化しない。それこそが10年レンズで見たときの危険性である。

# １．今すぐ改善すべき課題

> 現時点で壊れている、または時間経過とともに修復コストが単調増加するもの。

## 1-1. ファームウェアに OTA 更新機構が存在しない 【最重要】

- **現状**: `esp_ota` / `ArduinoOTA` / `HTTPUpdate` / `Update.begin` いずれも全木検索でヒットなし。`firmware/src/main.cpp` は起動→WiFi→取得→表示→`esp_deep_sleep_start()`(88-92行)のみで、アプリパーティションに触れる経路がない。`platformio.ini` にOTA用パーティションテーブル指定もない。
- **なぜ今か**: 配備済みデバイスのバグ修正手段が「額縁を外し、筐体を開け、USBで再書き込み」しかない。しかもOTA導入自体がパーティションテーブル変更を要する＝**最後の1回だけは必ずUSB書き込みが必要**。デバイスを増やすほど物理再書き込み負債が積み上がるため、着手が1台遅れるごとにコストが増える。後述 1-2 のような firmware 側バグの恒久修正も、OTA がなければ配れない。
- **方向性**: デバイスは既に毎周期サーバへHTTPアクセスしているので、**wake時のpull型OTA**が自然。画像取得時にサーバがファームウェアバージョンヘッダを見て、更新があれば `X-Firmware-Update: <url>` 等を返し、デバイスは `esp_https_ota`(または Arduino `HTTPUpdate`)で更新して再起動する。必要なのはOTAデュアルパーティション化・バージョン定数の埋め込み・失敗時ロールバック(`esp_ota_mark_app_valid_cancel_rollback`)の3点。CI は既に `v*` タグでバイナリをリリースしており(`ci-firmware.yml:45-57`)、配信元の素材は揃っている。

## 1-2. `X-Sleep-Seconds` を無検証で信頼している(実質文鎮化の恐れ)

- **現状**: `main.cpp:70-77` で `sleepSeconds = sls.toInt()` に上限も下限もない。`deepSleep()` は `seconds * 1000000ULL`(90行)にそのまま渡す。`int` が負や巨大値になった場合、uint64 変換で事実上無限のスリープになる。通信は平文HTTPがデフォルトで、HTTPS でも `setInsecure()`(36行)のため証明書検証なし。READMEの「最低180秒」はサーバ側実装のみ。
- **なぜ今か**: サーバのバグ・設定ミス・LAN内のなりすましのいずれか1回で、`X-Sleep-Seconds: 2000000000` を受けたデバイスは**数十年スリープ＝RSTボタン以外に回復手段がない状態**になる。OTAがない現状(1-1)ではファーム側の信頼バグは配布修正もできない。修正は数行。
- **方向性**: firmware 側で `clamp(sleepSeconds, 60, 86400)` を入れる。防御は契約の両端で行うのが原則で、サーバ側バリデーションは「相手も自分が書いたから大丈夫」というモノレポ特有の錯覚である。デバイスは一度家の壁に掛かれば独立した分散システムの一端になる。

## 1-3. クリーンクローンからシステムを再現できない(旧名 `wspf` 残骸 + `make scan` 不在)

- **現状**(すべて再検証済み):
  - `api/config/service.yaml.example:36` が `src_path: /mnt/wspf` を指すが、compose のマウントは `/mnt/wisp`(`compose.yaml:29`)
  - `api/config/config.yaml.example:6` が `dsn: /data/wspf.db`(実運用は `wisp.db`)
  - `Makefile:31` の MySQL 用 sed は `dsn: ./data/wisp.db` を置換しようとするがテンプレート実体は `/data/wspf.db` → **パターン不一致で無言の空振り**(mysql選択時に起動不能な設定が生成される)
  - `Makefile:126` と `README.md` が案内する `make scan` という**ターゲットは存在しない**(実在するのは `dev-setup` / `up` / `samples` のみ)
- **なぜ今か**: 現在動いているのは、**gitignore された手修正済みローカル設定**の上でだけである(`api/.gitignore` が `config/*.yaml` を除外)。つまりリポジトリにコミットされているのは「壊れたテンプレートだけ」。ディスク故障や新マシン移行(10年なら必ず起きる)の瞬間に、オンボーディング手順が最初のステップで死ぬ。5年後の自分は `wspf` が旧名であることすら覚えていない。
- **方向性**: (a) `.example` 2ファイルの `wspf` を `wisp` に統一、(b) `make scan`(`docker compose exec api ./wisp catalog scan` 相当)を実装、(c) sed パターン修正。再発防止として、**CI に「fresh clone スモークテスト」**(example設定コピー→compose up→scan→`/health` と `/pf/dev/image/random.bin` を叩く)を1本足す。これは 2-1・2-6 で述べるドリフト全般の検出器としても働く。

## 1-4. バックアップ戦略が一切ない(かつ WAL 運用で単純コピーは壊れる)

- **現状**: `backup` / `mysqldump` / `.backup` / `VACUUM INTO` に該当するコード・スクリプト・ドキュメントがゼロ。タグ、可視性フラグ、取得画像(`ImageData`)などシステムが生成した全状態は `api/data/wisp.db` の1コピーのみ。さらに WAL モード運用で `wisp.db-wal` が約17.5MB 未チェックポイントのまま存在するため、思いつきの `cp wisp.db` は**コミット済みデータを欠いた不整合コピー**になる。
- **なぜ今か**: 10年でディスク故障はほぼ確実に起きる。写真原本は `:ro` マウントで安全だが、数年分のキュレーション(タグ付け・除外設定)は再構築不能。バックアップは「事故の前日」までに存在しなければ意味がない。
- **方向性**: cron(またはホストのlaunchd)で `sqlite3 wisp.db "VACUUM INTO '/backup/wisp-$(date +%F).db'"` を日次実行し、世代ローテーション＋別ディスク/クラウドへ同期。WAL 下でもオンラインで一貫スナップショットが取れるのがこの方式を選ぶ理由。手順は README に明記する(「正しいバックアップ方法が非自明」自体が罠のため)。継続レプリケーションまで求めるなら 3-5 の Litestream 案。

## 1-5. `system prune` が二重に壊れている

- **現状**(再検証済み): `api/app/infra/repository/system.go:18-25` の `DropAndRecreate()` は (a) `PRAGMA writable_schema` 等 **SQLite 専用 DDL** のため MySQL では動かず、(b) 再作成が `AutoMigrate(&model.Image{})` のみで、`registry.go` が管理する `Tag` / `ImageTag` を落としたまま復元しない。実行後は `FindImagesWithoutTags`(`tag.go:64`)が存在しないテーブルを参照してタグ機能が壊れる。
- **なぜ今か**: 「めったに使わないメンテナンスコマンドが静かに壊れている」は、数年後の障害対応中——最も判断力が落ちている瞬間——に薄れた記憶で実行されて着火する類のバグ。
- **方向性**: `model.AllModels()` で全テーブル再作成し、DDL は GORM の `Migrator().DropTable()`(方言非依存)に置換する。もしくは MySQL 側では明示的にエラーを返す。修正までの間、少なくともコマンドヘルプに警告を出す。

## 1-6. 本番イメージが lockfile を無視してビルドされている

- **現状**(再検証済み): `frontend/Dockerfile:9` が `RUN npm install --frozen-lockfile`。`--frozen-lockfile` は yarn/pnpm のフラグで **npm は黙って無視**し、caret 範囲(`package.json` はほぼ全部 `^`)を満たす最新を解決する通常 install になる。CI は `npm ci` で正しい(`ci-frontend.yml:34`)ため、**CIが検証した依存ツリーと出荷イメージの依存ツリーが乖離しうる**。
- **方向性**: `npm ci` に変更。1語の修正で「CIでは通ったのに本番だけ壊れる」クラスの事故を恒久的に封じる。

## 1-7. `.env` の `API_BASE_URL` がフロントエンドに届かない(LAN内他端末からの利用が壊れている)

- **現状**: `dev-setup` は「他端末からアクセスするならLAN IPを」と案内して `.env` に `API_BASE_URL` を書かせる(`Makefile:88-97`)が、`compose.yaml:54` は `VITE_API_BASE_URL=http://localhost:9002` を**ハードコード**しており `.env` の値を参照しない。結果、スマホ等からSPAを開くとAPIだけ `localhost` を向いて無言で失敗する。
- **方向性**: `- VITE_API_BASE_URL=${API_BASE_URL:-http://localhost:9002}` と1行で配線する。同一概念に3つの名前(`API_BASE_URL` / `VITE_API_BASE_URL` / `window.__env__.API_BASE_URL`)が存在するのが根本原因なので、あわせて README の「ビルド時環境変数は使わない」という記述(`frontend/README.md:50` — `config.ts:10` の `import.meta.env` フォールバックと矛盾)も現実に合わせて修正する。

## 1-8. 画面の心臓部が保守放棄された beta ライブラリの非公開APIに依存

- **現状**: `vue-virtual-scroller: ^2.0.0-beta.8`(`package.json:27`)。beta.8 がこの系列の最終公開版で、stable v2 は存在せず、维持されている v1.1.2 には必要な `grid-items` API がない。型定義は空宣言(`src/types/vue-virtual-scroller.d.ts`)で統合部全体が `any`。さらに `PhotoGrid.vue:126-150` は 1px `scrollTop` ナッジと `(scrollerRef.value as any)?.updateVisibleItems?.(false)` という**非公開メソッド呼び出し**で beta.8 固有の挙動を補正しており、optional chaining のためメソッドが消えても**エラーなく黙って壊れる**(黒い歯抜けが無症状で再発する)。この経路を検証するテストはない(`PhotoGrid.spec.ts` はスクローラを完全スタブ)。
- **なぜ今か**: ここはアプリの一等地であり、上流修正は今後永遠に来ない。Vue / Vuetify / ブラウザ側の変化は今後10年止まらないので、時間はこの依存に対して一方的に不利に働く。
- **方向性**: **即日**——ワークアラウンドを専用ラッパーコンポーネントに隔離し、黒歯抜け経路を踏むE2Eを1本追加(silent failure を可視化する)。**中期**——置換。候補は保守されている `@tanstack/vue-virtual`(ヘッドレスで自前グリッドと相性が良い)か、本アプリのタイルは均一サイズなので自前の単純グリッド仮想化(最も難しいケースではない)。「動いているものを触るな」がこのケースで通用しないのは、壊れたときに直す手段が既に存在しないからである。

# ２．パラダイム乖離 — 表面上は動いているが、この方法論を正しいと思わないでほしい

> 今日まで問題を起こしていないのは、規模が小さい・全コンポーネントを同一人物が同時に更新している・記憶が新しい、という**時間とともに失われる前提**に依存しているため。

## 2-1. スキーマ管理が GORM `AutoMigrate` オンリー(マイグレーション履歴が存在しない)

- **現状**: スキーマ変更手段は `WISP_AUTO_MIGRATE=1` で起動時に走る `conn.AutoMigrate(model.AllModels()...)`(`app/di/di.go:63-67`)のみ。バージョン管理されたマイグレーションはゼロ。
- **なぜ乖離か**: AutoMigrate は「列・インデックスの追加」しかできない。**リネーム・削除・型変更・データ移行(backfill)の表現手段がなく、いつ何が変わったかの履歴も残らない**。数年運用したDBと新規作成DBが静かに乖離し、差分の由来を誰も説明できなくなる——これが業界がマイグレーションをコードとして版管理する(schema-as-code with history)方向に収斂した理由。struct 定義がスキーマの唯一の真実に見えるのは、変更が「追加」だけで済んでいる初期だけの錯覚である。
- **方向性**: テーブルが3つの**今のうちに** goose / golang-migrate / atlas のような軽量ツールを導入し、以後の変更は必ず番号付きマイグレーションで行う。AutoMigrate は開発時の使い捨てDB専用に降格する。導入コストはスキーマサイズに比例するので、今が最安値。

## 2-2. コンポーネント間契約がすべて暗黙(バージョン交渉・強制手段なし)

- **現状**:
  - firmware→server はパス中のMACのみ。ファームウェアバージョンも表示モデルも申告せず、応答バイナリを**長さ・形式の検査なしにパネルへ直送**(`epd7in3e/EPaperDisplayImpl.cpp:159-180` は期待サイズ192,000バイトとの照合をしない)
  - `service.yaml` の `api_version` はパースされる(`config_parser.go:71`)が**どこからも読まれていない**——バージョニングの器だけあって配線がない
  - OpenAPI 仕様は存在する(`api/api/swagger.yaml`, 358行)が、コードとの一致を検証するものが何もない
  - frontend↔api は手書きDTOの二重管理(`frontend/src/types/index.ts:2-14` ⇄ `handler/response/image.go:8-10`)で、フィールド名変更は両側のテストを全部通過してから実行時に壊れる
- **なぜ乖離か**: firmware と server は**リリースサイクルが異なる独立配備物**であり、これは好むと好まざるとに関わらず分散システムである。分散システムで契約を暗黙にすると、破壊的変更の検出地点が「壁に掛かった、更新が止まったデバイス」——最悪の場所——になる。「両側とも自分が書くから同期できる」は10年スパンでは成立しない(5年後の自分は他人)。
- **方向性**: (a) firmware がリクエストにFWバージョン+モデルをヘッダで申告し、server は応答バイナリに1バイトのフォーマットバージョン(または応答ヘッダ)を付けて firmware が照合する。旧バージョン申告には旧フォーマットで応える——これで両者が独立に更新可能になる。(b) swagger.yaml をCIで実装と突き合わせる契約テストを1本。(c) frontend の型は swagger からの生成に置換。1-3 のスモークテストと合わせれば、契約の破壊は必ずCIで止まる。

## 2-3. ビルドの再現性を registry の善意に預けている(ツールチェーン無固定)

- **現状**: `platformio.ini` は `platform = espressif32`(**バージョン指定なし**)、CI は `pip install platformio`(無固定、`ci-firmware.yml:41`)。Docker ベースイメージも `debian:bookworm-slim` / `node:22-alpine` / `nginx:1.27-alpine` と浮動タグ(digest 固定なし)。
- **なぜ乖離か**: 「今日ビルドが通る」ことと「2033年に同じバイナリが作れる」ことは別物である。espressif32 プラットフォームは Arduino core 2.x→3.x(IDF 4→5)で実際に大規模破壊を経験済みで、無指定は「そのとき registry が返すもの」への白紙委任に等しい。ハードウェアを持つプロジェクトでは、**再現ビルドできない＝配備済みデバイスに対する修正能力の喪失**を意味する(1-1のOTAが入っても、ビルドできなければ配るものがない)。
- **方向性**: `platform = espressif32@X.Y.Z` と PlatformIO 自体のバージョンを固定(2行)。Docker は digest 固定し、更新は Dependabot 経由の**意識的な**行為に変える。固定は「更新しない」ことではなく「更新を選択的にする」ことである、というのがこのパラダイムの要点。

## 2-4. 設定の誤りを黙って握りつぶす

- **現状**: 未知のカタログ種別は警告して捨てる(`config_parser.go:55,206`)、未知のフィルタ名は `default: // do nothing`(`usecase/catalog.go:414`)、日時パース失敗は `t, _ :=` で無視(`config_parser.go:143-158`)、yaml.v2 は未知キーを黙殺(例: `config.yaml` の `database.log:` はどこにもマップされない)。さらに `service.yaml.example` は実装に存在しない `playwright-go` / `lua` カタログや `auto_gamma` フィルタを文書化している。
- **なぜ乖離か**: 家電型システムにおいて最悪の故障クラスは「エラー」ではなく「**黙って違う動作をする**」である。フィルタ名のタイポは、エラーではなく「なんとなく違う写真の出方」として現れ、数年後に「なぜこのカタログだけ変なのか」という追跡不能なデバッグになる。Fail-fast(起動時に設定全体を検証して未知項目を拒否する)が構成管理の標準になったのはこのため。
- **方向性**: yaml.v3 の `KnownFields(true)` で未知キーを、フィルタ/カタログ種別のswitchで未知値を、それぞれ**起動エラー**にする。緩和が必要なら `--lax` フラグで旧挙動を残す。あわせてテンプレートから未実装機能の記述を削除(2-6)。

## 2-5. UI協調を `window` イベントバスと壁時計タイマーで行っている

- **現状**: PhotoGrid→Timeline の通信が `window.dispatchEvent(new CustomEvent('viewport-timeline-update'))`(`PhotoGrid.vue:112`)で、Pinia ストアの脇を素通りしている。しかも正しさが「スクロールdebounce 150ms(`PhotoGrid.vue:121-123`) < クリック後抑制 300ms(`TimelineScrollbar.vue:50,68-71`)」という**どこにも明文化されていない時間差の不等式**に依存する。テストはイベントを直接発火するだけで、この競合は未検証。
- **なぜ乖離か**: 状態管理に Pinia を導入済みのアプリで、一部のデータフローだけグローバルイベントに逃がすと、将来の保守者(＝未来の自分)はストアを読んでも挙動を再構成できない。壁時計ベースの競合解決は、遅いデバイスやスクローラ置換(1-8で不可避)で無音で崩れる。「動くまで数値を調整する」は同期設計の代替にならない。
- **方向性**: スクロール位置・アクティブ月をストアの状態として一元化し、Timeline クリック時の抑制は「タイマー」ではなく「目標位置に到達したか」の**位置比較**で解く。イベントバスは削除。1-8 のラッパー導入と同時に行うのが効率的。

## 2-6. ドキュメントが実装ではなく願望を記述している

- **現状**:
  - `CLAUDE.md` は `app/domain/ai/`・`app/infra/llm/`・`usecase/generate.go`・`pipeline_runner.go`・3層のpipeline実行テーブル群を詳述するが、**これらはコードベースに存在しない**(実在する「AI」は plain HTTP POST の `usecase/tagging.go` のみ)
  - その `CLAUDE.md`(最良のアーキテクチャ文書)自体が **gitignore されている**(`.gitignore:19`)
  - `route.go:18` に「Management API — requires authentication」とコメントがあるが、**認証ミドルウェアは存在しない**
  - `README.md:33` は EPD13IN3E を「tested」と記すが `TODO.md:33` は実機未検証と記す。WiSPの正式名称もファイル間で不一致(`swagger.yaml:6` vs README)
- **なぜ乖離か**: 1人×10年のプロジェクトにおける最重要協働者は「記憶を失った未来の自分」であり、その人物はドキュメントを信じて行動する。存在しないサブシステムの記述は幽霊を追わせ、**セキュリティ特性について嘘をつくコメント**(認証)は「ポートフォワードしても大丈夫」という誤判断の根拠になる。ドキュメントは現実のみを記述し、願望は Issue/TODO に隔離する——これが「docs as spec」の規律である。
- **方向性**: CLAUDE.md を実装と一致するまで刈り込み、内容を `ARCHITECTURE.md` としてコミット対象にする。`route.go:18` のコメントは削除するか、実際に認証を入れる(`e.Group("/api")` の構造上、ミドルウェア1行で足せる設計にはなっている)。「tested」表記は実態に合わせる。

## 2-7. 本番デプロイという成果物が存在しない

- **現状**: リポジトリ内の compose は2つとも `target: development` +ソースbind-mount+ホットリロード構成。CI は `ghcr.io/.../api:latest`・`frontend:latest` を発行するが、**それを消費する定義がリポジトリのどこにもない**。`restart:` ポリシーも全サービス未設定。イメージタグは api が `latest` のみ(`ci-api.yml:67`)でロールバック先が存在しない。
- **なぜ乖離か**: 「本番構成は頭の中にある」は、停電後にスタックが自動復帰しない・不良デプロイを`latest`しかないので巻き戻せない・新マシン移行時に記憶から再構築する、という形で請求書が届く。firmware は `v*` タグ→リリース資産という正しい型を既に実践しており(`ci-firmware.yml:45-57`)、サービス側だけがその規律から漏れている。
- **方向性**: GHCR イメージ+`restart: unless-stopped`+名前付きボリュームの `compose.prod.yaml` をコミットし、git タグからイメージへ semver タグを打つ(firmware と同じ型に揃えるだけ)。dev compose が nginx/CSP/env.js 生成経路を一切通らない問題(本番でだけ動くコード)も、prod compose をローカルで起動可能にすることで解消する。

## 2-8. 公開リポジトリに LICENSE がない(かつ GPLv3 ファームウェアと同居)

- **現状**: `firmware/LICENSE.md`(GPLv3)とフォントライセンスのみ。ルート・api・frontend にライセンスなし。
- **なぜ乖離か**: 公開リポジトリでライセンス不在は法的に「All rights reserved」であり、将来の協力者どころか(転職先の規定次第では)**自分自身の再利用すら曖昧**になる。GPLv3 の firmware(Waveshare 由来コードの系譜も要確認)と無ライセンスの api/frontend の混在は、コピーレフトの及ぶ範囲を不明瞭にする。
- **方向性**: 今、意図的に決める。典型解は api/frontend を MIT または Apache-2.0、firmware はドライバの由来を確認の上 GPLv3 維持。10年後に決めるより今決める方が、混入した第三者コードの追跡が容易。

# ３．提案 — 現行でも正しいが、こういう方法もある

> 現状の判断はスコープに対して妥当。より良くなりうる選択肢として提示する。

## 3-1. `rnd` 更新失敗時、エラー画像ではなく写真を返す

`FindByRandom` は選択済みの写真があっても、乱数再シードの `Update("rnd", ...)` が失敗するとエラーを返し(`app/infra/repository/image.go:176-178`)、額縁にはエラー画像が出る。ディスク満杯・読み取り専用化(10年なら起きる)の日に、**表示できる写真があるのにエラー画面を出す**のは無人アプライアンスとして損な取引。簿記エラーはログに落として写真を返す方が、このプロダクトの価値関数に合う。現状がコメント付きの意図的判断であることは把握した上で、逆側を推す。

## 3-2. 障害中のエラー画面は1回だけ描く(+エラースリープ中のBOOT復帰)

WiFi失敗→エラー描画→1hスリープ(`main.cpp:159-167`)は、サーバが1週間落ちると**最も電力を食う操作(フルリフレッシュ)を約168回**繰り返す。RTCメモリに「エラー描画済み」フラグを持ち、2回目以降は描画スキップでスリープ再試行のみにする。あわせて `esp_sleep_enable_ext0/ext1` で BOOT ボタンをwake源に加えると、24hエラースリープ中(`main.cpp:203-207`)の唯一の脱出手段がRSTである現状も改善する。

## 3-3. 電池の低電圧保護

電圧監視・低電圧時の長期スリープが皆無で、LiPo をディープ放電まで引っ張りうる。10年で最初に死ぬ部品はほぼ確実に電池セルであり、ソフトだけでも「電圧低下時は更新間隔を伸ばし最終的に無期限スリープ」で寿命を大きく延ばせる。ADC分圧が無いボードでは次のハードリビジョンでの課題として記録しておく価値がある。

## 3-4. SoftAP プロビジョニングに WPA2 を

現在は完全オープンAP(`WiFiManager.cpp:87` — `softAP(ssid, NULL)`)上の平文HTTPフォームで WiFi パスワードを送る。窓は限定的(セットアップ時のみ)だが、MAC由来のデバイス固有パスワード(筐体ラベルに印字)で閉じられる。フォームのHTML/JSONエスケープ(`WiFiManager.cpp:97-111,229-238`)は既に丁寧で、あと一歩の位置にいる。

## 3-5. バックアップの発展形: Litestream / VACUUM INTO の常時化

1-4 の日次スナップショットで最低線は守れるが、SQLite なら [Litestream] のサイドカーで S3/バックアップ先へ**継続レプリケーション**する構成が、運用の手数ゼロで RPO を分単位にできる。compose にサービスを1つ足すだけで済むのが SQLite を選んだこと(正しい選択)の配当。

## 3-6. 純ロジックのネイティブテスト

`test/` は空(PlatformIO 雛形のみ)だが、`RLEDecoder.h` や `epd13in3k` の `splitPlanes()`(2bpp→プレーン分割)はハードウェア不要の純関数で、`[env:native]` によるホスト側ユニットテストが安価に書ける。「後年リファクタで最も壊れやすいビット操作」に保険を掛ける場所として費用対効果が最も高い。api 側も、デバイス向けバイトパイプライン(dither/encoder→handler)がテスト最薄なので、ゴールデンファイル比較テスト(既知入力→既知バイナリ)を1本足すと 2-2 の契約固定にも効く。

## 3-7. `on_new_file` フックは `sh -c` 置換ではなく argv 渡しに

`usecase/catalog.go:482-489` は `{file}` を文字列置換して `sh -c` に渡すため、ファイル名にシェルメタ文字があると注入になる。自分の写真ディレクトリという前提では実害は低いが、`exec.Command(prog, args..., filePath)` の argv 渡しなら同機能をリスクゼロで実現できる。10年寝かせる罠を1つ減らす。

## 3-8. ヘキサゴナル純度の残り数%(急がない)

ドメインモデルに `gorm.DeletedAt` と永続化タグが載る(`model/image.go`)、`uber/dig` はこの規模(プロバイダ約10個)なら手書きワイヤリングと等価——いずれも**今の規模では実害のない実利主義**。ただし「domain は framework 非依存」という自らの規律の例外であることは認識しておき、モデルが増える局面で永続化structとドメインstructを分けるか判断する。dig を剥がす必要はない。

## 3-9. CI 赤化の未来コスト管理

`npm audit --audit-level=high` がブロッキング(`ci-frontend.yml:36`)のため、休眠期間中にコード変更ゼロでもCIが赤くなる(特に修正版が永遠に出ない 1-8 のスクローラ経由)。audit を非ブロック化するか、修正不能な advisory の allowlist 運用に。逆に api イメージには Trivy/SBOM が**ない**(frontend にはある)ので、LAN で画像デコードを行う Go サービス側にこそ揃えたい。firmware CI も3ターゲット中2つしかビルドしておらず(`ci-firmware.yml:27-30`)、13.3インチ系ドライバ2種はビルドゲートの外で腐る——コンパイルだけでも全ターゲット通す。

## 3-10. 小粒クリーンアップ(まとめて半日)

- 参照されない `FALLBACK_IMAGE_URL` 群(`config/network.h:13-24`、feature ブランチ直リンクと `<user>/<repo>` プレースホルダ)を削除または実装
- `Photo` 型の3重定義(`types/index.ts` / `PhotoGrid.vue:63-68` / `PhotoItem.vue:75-80`)を import に統一、タイムライン幅 120px 等のJS/CSS二重管理定数を定数化
- 死んでいる `GET /api/devices`(`route.go:31`)、未使用 `#define LED 2`(`main.cpp:15`、S3では `EPD_PWR_PIN=2` と衝突)、`api/data/wisp.dbb`(タイポ空ファイル)、ローカル残骸ブランチ(`develop-old` 等)の整理
- `api/.dockerignore` を作成(現状 `COPY . .` が 31MB のDB+17MBのWALをビルドコンテキストに同梱)

# ４．プラスポイント — これ以上の最適解を求めない

> 10年運用の観点で「正解を引いている」設計。将来のリファクタでも壊さないこと。

## 4-1. デバイス契約のグレースフル・デグラデーション(本レビュー最大の美点)

サーバはいかなるエラー時も、人間可読のメッセージを**要求されたベンダー形式の正規 e-paper バイナリとして描画して返し**、`X-Sleep-Seconds: 3600` でバックオフさせる(`handler/catalog.go:192-219, 277-321`)。無人デバイスが壊れた応答を受け取る経路が構造的に存在しない。エラーが「額縁に読める文字で出る」ことは、リモート診断手段のないアプライアンスにおける最良のテレメトリでもある。この形以上の解は思いつかない。

## 4-2. ファームウェアの「必ず deep sleep に収束する」性質

全ブロッキング経路にタイムアウトが張られている——busy待ち60s(`epd7in3e:241-255`)、ストリーム受信30s、WiFi 15s、HTTP 30s。`TODO.md:1-16` はこれらが意図的に後付け整備されたことを示す。**どんな故障モードでもハングして電池を空にすることがない**という証明可能な性質は、電池駆動の壁掛けデバイスで最も価値のある不変条件。WiFi再接続もチャネル/BSSIDヒントで通常経路のスキャンを省き、NVS書き込みは値変化時のみ(フラッシュ摩耗回避、`WiFiManager.cpp:44-59, 358-375`)と、電池と寿命への配慮が一貫している。

## 4-3. 表示ドライバの完全ベンダリング + クリーンな抽象

`lib_deps` は空。Waveshare 4機種のドライバは全てツリー内にあり、`EPaperDisplay` インターフェース + `EPaperFactory` の背後に整列している。外部レジストリの消滅・上流の破壊的変更でリビルドが壊れる経路がゼロ。2-3 のツールチェーン固定が済めば、ファームウェアは真に自己完結する。

## 4-4. DBを肥大させないデータ設計

ファイル由来の写真はDBに256pxサムネイルとパスのみ(原寸は都度ディスクから読む)、`ImageData` blob は HTTP/生成カタログ限定かつ `depth` 上限のFIFO退避付き(`fetch.go:104-121`、`image.go:191-206`)。「blob同居」は一見負債に見えるが、実際には**有界**であり、SQLite ファイルが際限なく育たない設計になっている。`excluded`(カタログ規則)と `deleted_at`(ユーザー操作)の分離も意図がコメントで明文化されており(`model/image.go:23-30`)、リストAPIの複合インデックスはこの述語を完全カバーする。

## 4-5. SQLite の運用プラグマが正しい

WAL + `busy_timeout=5000` + `synchronous=NORMAL` + 外部キー有効化をDSNで指定し、さらに**起動時にWALモードが実際に効いているか検証する**(`infra/sqlite.go:42-76`)。純Goドライバ(glebarez/sqlite)の採用はクロスコンパイルも単純化する。自宅サーバ規模のSQLite運用としてお手本の構成。

## 4-6. メモリと停止シグナルへの一貫した配慮

HEIC デコードの巨大なメモリ消費を前提に、セマフォで有界化したワーカープール、goroutine毎の独立パイプライン(共有状態なし)、`GOMEMLIMIT` の使い方まで compose コメントで文書化(`compose.yaml:16-22`)、全長時間処理に SIGINT/SIGTERM キャンセル伝播(`usecase/catalog.go:126-231` ほか)。「なぜこの並行度なのか」の理由がコードとコメントに残っているため、10年後にチューニングし直せる。

## 4-7. 1人保守を支えるガードレール群

slog による構造化ログ+リクエストID伝播、`gosec`/`errcheck`/`forcetypeassert`/`cyclop`(複雑度上限15)を含む厳格な golangci 設定、TypeScript strict、path-filtered CI、最小権限トークン(`packages: write` をビルドジョブのみに限定)。**規律を人間の記憶ではなく機械に持たせている**点が10年向き。

## 4-8. フロントエンドの自己完結性とセキュリティ姿勢

フォント(@fontsource/poppins)とアイコンを自己ホストしCDN依存ゼロ——Google Fonts の仕様変更やオフライン環境に対して10年間中立。enforcing CSP+コンテナ起動時のorigin動的注入、`env.js` の `no-store`、dotfile遮断、ハッシュ資産のimmutableキャッシュ(`nginx.conf`)。ランタイム env 注入(1イメージでどのバックエンドにも向けられる)は12-factorの正しい適用で、機構の硬さ(3-10)はともかく**設計としてはこれが正解**。NDJSONリーダ(`services/ndjsonStream.ts`)は部分行バッファ・abort時の `reader.cancel()`・`finally` での `releaseLock()` まで書き切られており、git履歴は競合バグを見つけて潰した過程を示している。

## 4-9. 秘密情報と原本データの衛生

実設定(`config/*.yaml`・`.env`・`env.js`)は gitignore され、履歴に鍵の混入なし(検証済み)。写真原本は `:ro` マウントで**システムが原本を壊す経路が構造的に存在しない**。LLM 連携がベンダーSDKではなくプレーンHTTPなのも、10年間のプロバイダ変遷に対する正しい絶縁。

## 4-10. firmware のリリース工程と `make dev-setup`

`v*` タグ→ターゲット別バイナリのリネーム→GitHub Release 添付+ラベル別チェンジログ(`ci-firmware.yml`, `.github/release.yml`)は、このリポジトリで唯一「バージョン付き・ダウンロード可能・巻き戻し可能」なリリースの型であり、2-7 はこれをサービス側に**複製するだけ**でよい。`make dev-setup` の対話式オンボーディング(DB選択・機種メニュー・LAN URL案内・サンプル画像DL・macOS/Linux sed差分吸収)も、1-3 の名前ドリフトさえ直せば模範的な導入体験。
