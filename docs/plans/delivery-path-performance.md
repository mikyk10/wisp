# 配信経路の性能改善 — 経緯と今後

- **対象**: 電子ペーパー配信経路 `GET /pf/:displayKey/image/random.*`
- **期間**: 2026-07-06(計画策定)〜 2026-08-04(P0〜P3 + エンコーダ最適化 完了)
- **計測環境**: Apple M3 Pro / 12MP (4000×3000) JPEG → WS7in3E (800×480)
- **詳細計画**: 回転・リサイズについては [improc-rotation-resize.md](improc-rotation-resize.md) を参照

| JPEG デコード | 48.7 ms | 48.7 ms | **未着手** |
| 画像パイプライン | 293 ms | **25.7 ms** | 完了 |

## 2. 完了した作業

### 2.1 回転の直交演算化(`c757506`, P1)

`bild transform.Rotate` は90°の倍数に高速パスを持たず、一般アフィン経路で**画素ごとに sin/cos を4回**呼び、`dst.Set()` に `color.RGBA64` を渡して**画素あたり2回ヒープ確保**していた。90°回転は本来ただの添字並べ替えである。

`disintegration/imaging` の直交演算を包む `improc/ortho` パッケージを新設し、`exif_rotation` / `crop` / `rotation` / `timestamp` の呼び出しを置換。EXIF 5/7 は「回転+反転の2パス」が `Transpose` / `Transverse` の1パスになった。

`bild transform.Crop` も全画素を RGBA 変換してから切り出していたため `imaging.Crop` に置換(0°経路の YCbCr 入力が 28.9 → 3.8 ms)。

**293 ms → 45.2 ms、確保回数 50.7M → 384K。**

### 2.2 EXIF回転と表示補正の融合(`d5f1270`, P2)

配信経路はフル解像度の画像を2回回していた(EXIF正規化 → 表示向き補正)。両者は8元の直交変換群 D4 の元なので合成できる。

`exif_rotation` に遅延形(`NewDeferredExifRotation`)を追加し、演算を `meta.PendingExifOp` に記録するだけにする。`crop` が明示的な8×8合成表で自分の補正と合成し、1回だけ適用する。

**45.2 ms → 30.4 ms。** 打ち消し合う構成(縦撮り写真 + 縦設置)ではフル解像度の回転が完全に消える。

### 2.3 timestamp のバッジのみ回転(`c7c274d`, P3)

日付を「写真の右下」に置くために画像全体を逆回転→描画→再回転していた。38万画素を2回回して1,110画素を配置していたことになる。バッジ側を回して該当する隅に合成する方式に変更。

**8.21 ms → 0.106 ms(角度依存も消滅)。**

### 2.4 エンコーダの画素ループ(`26f845c`)

`img.At(x,y)` が返す `color.Color` インターフェースへの boxing が**画素あたり1ヒープ確保**、加えて `map[uint32]int` のプローブが画素あたり1回。

パイプラインが実際に produce する `*image.RGBA` / `*image.NRGBA` は `Pix` から直読みし、パレット索引を256要素配列に。3つのパネル形式は同じ索引を違うビット配置で詰めるだけなので、色解決は共有スライスへ1回だけ行う。

**5.79 → 0.99 ms(7.3")、28.74 → 4.84 ms(13.3")、確保回数は画素数分 → 3。**

### 2.5 パレット順の決定化(`04aa66d`)

`slices.Collect(maps.Values(epd.Palette()))` が Go の map 反復順ランダム化を拾い、**同じ写真が実行のたびに違う結果になっていた**(Floyd-Steinberg で15%の画素、production 設定の bayer/simple では1〜35画素)。

見た目の実害はほぼ無かった(色の入れ替わりが双方向ほぼ同数で、局所平均色が保存されるため)が、**再現性がないとパイプライン全体をテストで固定できない**。エンコーダ改修の検証で実際に障害になった。パネルの色索引順に並べるだけで解決。

## 3. 計画が外れた点(記録)

実施中に判明した、当初計画の誤り。同種の判断をする際の参考として残す。

| # | 計画の想定 | 実際 |
|---|---|---|
| 1 | timestamp の二重回転は補間により**パレット外の中間色を生む品質バグ** | **誤り。** `bild` が supersample に入るのは90°の倍数**でない**角度のときだけ。旧実装も最近傍で無劣化だった。P1 でゴールデン32ケースがビット一致したことで裏付けられ、想定していた「再祝福」も不要だった |
| 2 | `exif_rotation` と `crop` は**両呼び出し元で必ず隣接** | **誤り。** 呼び出し元は3箇所あり、`usecase/catalog.go:266`(スキャン時サムネイル)は `exif_rotation` 単独。無条件に遅延させると回っていないサムネイルが DB に保存されるところだった。コンストラクタを即時形/遅延形に分けて対応 |
| 3 | 0°経路の YCbCr コストは `transform.Rotate` の問題 | **不十分。** `transform.Crop` も `AsShallowRGBA` で全画素変換していた。回転をスキップしても変換が残るため、Crop も置換が必要だった |
| 4 | リサイズが P1/P2 後に残る最大コスト | **P0 時点では偽、P3 時点で真。** P0 ではリサイズは全体の5%未満だった。回転を潰した結果 53% になり、前提が後から成立した |
| 5 | (計画外)パイプライン全体は再現可能 | **誤り。** パレット順が非決定的だった(2.5) |

## 5. 今後の選択肢

残り 75.4 ms の内訳と、狙える手段。

| 案 | 対象 | 見込み | 適用範囲 | リスク・コスト |
|---|---|---|---|---|
| **A. JPEG 縮小デコード** | デコード 48.7 ms + resize 13.7 ms | **約50 ms 削減** | 全構成 | C ライブラリ依存が増える |
| **B. 事前レンダリング** | 全体 | 応答が実質ゼロに | 全構成 | アーキテクチャ変更 |
| **C. P4 リサイズフィルタ** | resize 13.7 ms | 数 ms | 全構成 | 実機目視が合格条件。**A をやると無意味になる** |
| **D. ディザ** | 8.1 ms | 不明 | 全構成 | third-party、手が入れにくい |
| **E. 回転をリサイズ後に** | 2.5 ms | 2.5 ms | compounding 構成のみ | クロップ・被写体点の座標系を全面書き換え。**割に合わない** |

### A. JPEG 縮小デコード(推奨)

Go 標準の `image/jpeg` には DCT スケーリングがない。libjpeg(-turbo) は 1/2・1/4・1/8 でデコードできる。4000×3000 を 1/4 で読めば 1000×750 で、800×480 パネルには十分。

- デコード 48.7 → 8〜12 ms
- **resize も激減**(元画像が小さくなるため)13.7 → 2 ms 程度
- **合計 75.4 ms のうち約 50 ms が消える**

コスト面は軽い。**すでに cgo は有効**(`goheif` が libde265 を C で抱えている)、ランタイムイメージも `debian:bookworm-slim` で glibc。

判断すべき点: 縮小デコードは出力画質が変わる(元画像の情報が減る)ため、**実機目視が合格条件**になる。C と ④ が同じゲートを通るので、実機に立つなら A を優先すべき。

### B. 事前レンダリング

パネルは定期的に起きてリクエストするので、次の1枚を先に `.bin` まで作って置けば応答は実質ゼロ。e-paper の書き換え自体が数秒かかるため、体感への効き方はこれが最大。サーバ CPU も1リクエストあたりほぼゼロになる。

パイプラインが決定的になった(2.5)ので、事前生成物と実時間生成物が一致することを保証できるようになった。

### 推奨順

1. **A**(縮小デコード)— 残コストの大半を占め、C を無意味にする
2. **B**(事前レンダリング)— 体感を決めるのはこれ。A の後なら生成コストも低い
3. **C**(P4)— A の後に、まだ必要なら
4. D / E は現状では割に合わない
