# 改修計画: 画像パイプラインの回転・リサイズ高速化

- **対象**: `api/app/domain/improc/`(exif_rotation / crop / rotation / timestamp)およびその呼び出し元
- **目的**: 電子ペーパー配信経路(`GET /pf/:displayKey/image/random.*`)の回転・リサイズ処理の高速化
- **制約**: ①改修量を最小にする ②ソースの理解可能性(「EXIF正規化→表示向き補正→クロップ→リサイズ」という段階構造)を損なわない
- **作成日**: 2026-07-06
- **改訂**: 2026-08-04 — P2(回転統合)・P3(timestamp 全面回転の廃止)を当初スコープに繰り入れ。P4(リサイズフィルタ選定)は最低優先とし、「原版からリサイズ→減色」の段階順序を不変の制約として明記

---

## 1. 現状分析

### 1.1 パイプラインの構造(配信経路)

`usecase/catalog.go:389-436` で組み立てられる順序(CLI `cmd/image.go:68-89` も同一構成):

```
デコード(フル解像度, 例 4000×3000)
  │
  ├─ [preSeq]
  │   1. exif_rotation  … EXIF向きを物理回転で正規化(フル解像度)
  │   2. crop           … 表示向き補正の物理回転(フル解像度)→クロップ→リサイズ
  │
  ├─ [dispSeq]  brightness 等の画素フィルタ(以降はディスプレイ解像度, 例 800×480)
  │
  └─ [postSeq]
      3. color_reduction … ディザ・減色
      4. timestamp(任意) … 逆回転→日付描画→再回転
      5. rotation(任意)  … 180°回転(Flip設定)
```

### 1.2 物理回転の発生箇所と回数

| # | 場所 | 実装 | 解像度 | 発生回数(最悪) |
|---|---|---|---|---|
| R1 | `exif_rotation/proc.go:24-47` | `bild transform.Rotate` / `FlipH` / `FlipV` | **フル** | 2回(EXIF 5/7 は回転+反転の2パス) |
| R2 | `crop/proc.go:45` | `bild transform.Rotate`(±90° or 0°) | **フル** | 1回 |
| R3 | `timestamp/proc.go:33-35, 61-63` | `bild transform.Rotate` ×2(逆回転→再回転) | 表示 | 2回 |
| R4 | `rotation/proc.go:28`(Flip設定時) | `bild transform.Rotate`(180°) | 表示 | 1回 |

最悪ケース(EXIF 5/7 の写真+縦設置+timestamp+Flip)で**物理回転6回**、うち3回がフル解像度。

### 1.3 律速要因(ライブラリ実装の確認結果)

- **`bild transform.Rotate` は90°の倍数に高速パスを持たない**(`bild@v0.13.0/transform/rotate.go`)。0°のみ早期return。90/180/270°でも一般アフィン経路に入り、**内側ループでピクセル毎に `math.Sin`/`math.Cos` を4回呼び、`src.At().RGBA()` のインターフェース呼び出しで色変換する**。90°回転は本来ただの添字の並べ替え(メモリコピー相当)であり、ここに桁違いの無駄がある。
- **`imgconv.Resize` は Lanczos 固定**(`imgconv@v1.1.4/resize.go:26` — オプションで変更不可)。最高品質だが最重量のフィルタで、直後に強いディザ・減色(6色/7色/4階調)が入る本用途では過剰品質の可能性が高い。
- ~~R3(timestamp)は減色**後**の画像を補間付きで2回回すため、速度に加えて**パレット外の中間色を生む品質バグでもある**~~ → **P1 実施時に誤りと判明(2026-08-04)**。`bild` が supersample(補間)に入るのは90°の倍数**でない**角度のときだけで(`rotate.go:40`)、本パイプラインが使う 0/±90/180° はすべて最近傍の添字写しである。R3 は速度と確保回数の問題のみで、画質は劣化していなかった。
- **`bild transform.Crop` も全画素を RGBA 変換する**(`resize.go:47-50` の `clone.AsShallowRGBA` → `clone.AsRGBA(SubImage)`)。回転を0°でスキップしても、この変換が残るため YCbCr 入力のコストは消えない(P1 で判明し、`imaging.Crop` に置換)。

### 1.4 前回指摘(無駄な回転)の正体

「EXIF正規化で1回回し、直後の crop で表示向きに合わせてまた回す」という**二段物理回転**が本質。~~`exif_rotation` と `crop` は両呼び出し元で必ず隣接しており~~ → **P2 実施時に訂正(2026-08-04)**: 呼び出し元は3箇所あり、`usecase/catalog.go:266`(スキャン時サムネイル)だけは `exif_rotation` 単独で crop が続かない。配信経路の2箇所では隣接しているので、2つの回転は合成して1回にできる。また `crop/proc.go:34-40` では `native≠installed` で−90°、`installed≠image` で+90°を**加算**しており、両者が打ち消し合って0°になる経路も、合成という考え方が実装に既に半分現れていることを示している。

## 2. 改修方針

3原則に集約する。各フェーズはこの原則の適用である。

1. **一般回転を直交演算に置き換える** — 90°倍数の回転・反転は sin/cos 不要の添字並べ替えで行う(無補間=無劣化のおまけ付き)
2. **フル解像度の物理回転は最大1回に統合する** — EXIF演算と表示向き補正は8元の直交変換群(D4)なので合成できる
3. **計測してから品質を落とす判断をする** — リサイズフィルタの変更は、ベンチと実機目視の両方が揃ってから

理解可能性の担保: プロセッサの分割・責務・適用順・`ImgMeta` の意味は**一切変えない**。変わるのは各プロセッサの内部実装のみで、「`crop.Apply` を出た時点で画素は設置向きに揃っている」という既存の不変条件を全フェーズで維持する。

回転ライブラリは新規実装せず **`disintegration/imaging`** を使う(`imgconv` 経由で既に依存グラフに存在。`Rotate90/180/270`・`Transpose`・`Transverse`・`FlipH/FlipV` が並列化された添字並べ替えとして実装済み)。自前実装を避けるのは、テスト済みコードの再利用が「最小改修量」の趣旨に最も適うため。

P2 計測から読み取れたこと:

- **パイプライン合計 45.2 ms → 30.4 ms(1.78倍)**。機械ノイズを排すため `BenchmarkDeliveryPipeline` を `fused` / `separate` の2サブベンチにし、**同一実行内で比較**した(同一実行で fused 30.4 ms / separate 54.0 ms)。P0 からの通算は **293 ms → 30.4 ms(9.6倍)**
- **ゴールデンは32ケースすべて無変更で green**。加えて `TestPreSeqGolden_DeferredMatchesImmediate` で「遅延+融合」と「即時2パス」が全32ケースでピクセル一致することを検証した
- allocs は 384K のまま変化なし(確保回数の削減は P1 で済んでいる)

**計画の前提誤りを1件修正**: §1.4 は「`exif_rotation` と `crop` は両呼び出し元で必ず隣接」としていたが、呼び出し元は2箇所ではなく**3箇所**あった。`usecase/catalog.go:266`(スキャン時のサムネイル生成)は `exif_rotation` 単独で、crop が続かない。ここで回転を遅延させるとサムネイルが回らないまま DB に保存されるため、コンストラクタを2つに分けた:

- `NewExifRotation()` — 即時回転。サムネイル経路が使用(挙動は改修前と同一)
- `NewDeferredExifRotation()` — `meta.PendingExifOp` に記録するのみ。配信経路2箇所が使用し、crop が消費する

呼び出し側で選択が見えるため、「誰が消費するのか」が読む位置で分かる。§6 の非スコープ「スキャン時のサムネイル生成経路」は、**触らないために**この分岐が必要だったという位置づけ。

P1 計測から読み取れたこと:

- **パイプライン合計 293 ms → 45.2 ms(6.5倍)、allocs は 50.7M → 384K(132倍減)**。回転1パスあたりの改善は13〜22倍
- **ゴールデンは32ケースすべて無変更で green。再祝福は不要だった**。§1.3 の「補間」という見立ては誤りで、`bild` は90°の倍数では supersample せず最近傍で写している(`rotate.go:40` の `absAngle%90 != 0` 判定)。つまり旧実装も無劣化であり、**P1 は純粋な速度・確保回数の改善で、画質は1ビットも動いていない**(§1.3・§7 の「品質バグ」記述を訂正)
- **`crop` の0°経路の YCbCr コストは `transform.Rotate` だけの問題ではなかった**。`bild transform.Crop` も `clone.AsShallowRGBA` で全画素変換してから切り出すため(`resize.go:47-50`)、回転をスキップしても変換が残る。`imaging.Crop` に置き換えて 28.9 ms → 3.8 ms
- 副作用として、**RGBA 入力の0°経路だけ 2.0 → 2.4 ms と微増**した(`imaging` は NRGBA に非乗算化しながら走査するため)。他経路の桁改善に対し無視できる
- **リサイズが最大の単一コストになった**(13.9 ms / 合計45.2 ms の約31%)。P4 の前提「P1/P2 後に残る最大のコスト」は P1 完了時点で成立した

P0 計測から読み取れたこと(計画時の想定との差分):

- **回転1パスあたり 24,000,000 allocs**(=1画素2回)。`bild` の内側ループが `dst.Set()` に `color.RGBA64` を渡すため、画素ごとにヒープ確保が起きている。速度差の主因は三角関数よりこちらの可能性が高い
- **`crop` の 0° 経路は YCbCr 入力で 28.9 ms**(RGBA 入力の 2.0 ms に対し14倍)。§2 で予測したとおり、`bild` の早期returnが RGBA 変換の後ろにあるため、回転しない場合でも全画素変換が走っている
- **resize は 14.1 ms しかなく、パイプライン合計 293 ms の 5% 未満**。「P1/P2 適用後に残る最大のコスト」という P4 の前提は P0 時点では成立していない。P1/P2 後に再評価する
- timestamp は角度ありで 8.21 ms(角度0の7倍)。1,536,060 allocs が計上されており、これも画素ごと確保

3. **実機確認**: `make up` → 実ディスプレイで代表写真(縦横・EXIF回転あり・被写体クロップあり・timestamp あり)を表示。特に P4 はこれを合格条件とする
4. **回帰範囲**: `go test ./...`、golangci-lint、CLI `image` コマンド(同じプロセッサを共有しているため自動的に検証される)

| 3 | 180° | Rotate(180) | Rotate180 |

## 6. 非スコープ

- HEIC/JPEG デコード自体の高速化(別課題。パイプライン合計では最大コストの可能性があるが本改修の目的外)
- スキャン時のサムネイル生成経路
- ディザ・減色アルゴリズム、エンコーダ
- `ImgMeta` の命名整理、プロセッサインターフェースへのエラー戻り値追加(長期レビュー 2-6 系の別件)

## 7. 想定効果とまとめ

- P1 だけで、全回転パスがピクセル毎三角関数の一般経路から添字並べ替えに変わる。加えて EXIF 5/7 と timestamp の**パス数自体が減る**。**実測でパイプライン合計 6.5倍・確保回数 132倍減、出力はピクセル完全一致**(想定していた「補間劣化の解消」は、そもそも劣化していなかったため該当なし。§1.3 訂正を参照)
- P2 でフル解像度の物理回転が構造的に最大1回になり、「EXIF理解に追いつくために足した回転」の重複が設計として解消される。P1 と併せて当初スコープとする
- P4 は残る最大コスト(リサイズ)への計測駆動の一手で、実機目視を合格条件とする。優先度は全フェーズ中最低とし、「原版からリサイズ→減色」の順序は維持する
- どのフェーズも `exif_rotation → crop → filters → color_reduction → post` という現行の段階構造・メタデータ契約を変えないため、読み手のメンタルモデルは従来のまま通用する
