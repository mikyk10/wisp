# 改修計画: 画像パイプラインの回転・リサイズ高速化

- **対象**: `api/app/domain/improc/`(exif_rotation / crop / rotation / timestamp)およびその呼び出し元
- **目的**: 電子ペーパー配信経路(`GET /pf/:displayKey/image/random.*`)の回転・リサイズ処理の高速化
- **制約**: ①改修量を最小にする ②ソースの理解可能性(「EXIF正規化→表示向き補正→クロップ→リサイズ」という段階構造)を損なわない
- **作成日**: 2026-07-06

---

## 1. 現状分析

### 1.1 パイプラインの構造(配信経路)

`usecase/catalog.go:389-436` で組み立てられる順序(CLI `cmd/image.go:68-89` も同一構成):

```
デコード(フル解像度, 例 4000×3000)
  │
  ├─ [preSeq]
  │   1. exif_rotation  … EXIF向きを物理回転で正規化(フル解像度)
  │   2. crop           … 表示向き補正の物理回転(フル解像度)→クロップ→リサイズ
  │
  ├─ [dispSeq]  brightness 等の画素フィルタ(以降はディスプレイ解像度, 例 800×480)
  │
  └─ [postSeq]
      3. color_reduction … ディザ・減色
      4. timestamp(任意) … 逆回転→日付描画→再回転
      5. rotation(任意)  … 180°回転(Flip設定)
```

### 1.2 物理回転の発生箇所と回数

| # | 場所 | 実装 | 解像度 | 発生回数(最悪) |
|---|---|---|---|---|
| R1 | `exif_rotation/proc.go:24-47` | `bild transform.Rotate` / `FlipH` / `FlipV` | **フル** | 2回(EXIF 5/7 は回転+反転の2パス) |
| R2 | `crop/proc.go:45` | `bild transform.Rotate`(±90° or 0°) | **フル** | 1回 |
| R3 | `timestamp/proc.go:33-35, 61-63` | `bild transform.Rotate` ×2(逆回転→再回転) | 表示 | 2回 |
| R4 | `rotation/proc.go:28`(Flip設定時) | `bild transform.Rotate`(180°) | 表示 | 1回 |

最悪ケース(EXIF 5/7 の写真+縦設置+timestamp+Flip)で**物理回転6回**、うち3回がフル解像度。

### 1.3 律速要因(ライブラリ実装の確認結果)

- **`bild transform.Rotate` は90°の倍数に高速パスを持たない**(`bild@v0.13.0/transform/rotate.go`)。0°のみ早期return。90/180/270°でも一般アフィン経路に入り、**内側ループでピクセル毎に `math.Sin`/`math.Cos` を4回呼び、`src.At().RGBA()` のインターフェース呼び出しで色変換する**。90°回転は本来ただの添字の並べ替え(メモリコピー相当)であり、ここに桁違いの無駄がある。
- **`imgconv.Resize` は Lanczos 固定**(`imgconv@v1.1.4/resize.go:26` — オプションで変更不可)。最高品質だが最重量のフィルタで、直後に強いディザ・減色(6色/7色/4階調)が入る本用途では過剰品質の可能性が高い。
- R3(timestamp)は減色**後**の画像を補間付きで2回回すため、速度に加えて**パレット外の中間色を生む品質バグでもある**(90°倍数を無補間実装に置換すれば消える)。

### 1.4 前回指摘(無駄な回転)の正体

「EXIF正規化で1回回し、直後の crop で表示向きに合わせてまた回す」という**二段物理回転**が本質。`exif_rotation` と `crop` は両呼び出し元で必ず隣接しており(間に他のプロセッサは入らない)、2つの回転は合成して1回にできる。また `crop/proc.go:34-40` では `native≠installed` で−90°、`installed≠image` で+90°を**加算**しており、両者が打ち消し合って0°になる経路も、合成という考え方が実装に既に半分現れていることを示している。

## 2. 改修方針

3原則に集約する。各フェーズはこの原則の適用である。

1. **一般回転を直交演算に置き換える** — 90°倍数の回転・反転は sin/cos 不要の添字並べ替えで行う(無補間=無劣化のおまけ付き)
2. **フル解像度の物理回転は最大1回に統合する** — EXIF演算と表示向き補正は8元の直交変換群(D4)なので合成できる
3. **計測してから品質を落とす判断をする** — リサイズフィルタの変更は、ベンチと実機目視の両方が揃ってから

理解可能性の担保: プロセッサの分割・責務・適用順・`ImgMeta` の意味は**一切変えない**。変わるのは各プロセッサの内部実装のみで、「`crop.Apply` を出た時点で画素は設置向きに揃っている」という既存の不変条件を全フェーズで維持する。

回転ライブラリは新規実装せず **`disintegration/imaging`** を使う(`imgconv` 経由で既に依存グラフに存在。`Rotate90/180/270`・`Transpose`・`Transverse`・`FlipH/FlipV` が並列化された添字並べ替えとして実装済み)。自前実装を避けるのは、テスト済みコードの再利用が「最小改修量」の趣旨に最も適うため。

### P1. 一般回転→直交演算への置換(最小改修・最大効果)

| | |
|---|---|
| 変更ファイル | `exif_rotation/proc.go`、`crop/proc.go`、`rotation/proc.go`、`timestamp/proc.go`(いずれも呼び出し行の置換のみ) |
| 内容 | `bild transform.Rotate/FlipH/FlipV` を `imaging` の直交演算に置換する。対応表(§5)をコードコメントとして残す。EXIF 5/7 は現行の「回転+反転の2パス」が `imaging.Transpose` / `Transverse` の**1パス**になる。`crop` は angle==0 のとき呼び出し自体をスキップ(現行は bild の早期returnに依存しており、YCbCr入力だと0°でも全画素のRGBA変換が走る) |
| 理由 | ピクセル毎 sin/cos の一般経路から添字並べ替えへ。処理構造・プロセッサ責務は完全に不変のため、改修量あたりの効果が最大。副次効果として90°回転が無補間=無劣化になり、R3 が減色後画像を汚す品質バグも消える |
| 検証 | ゴールデンは**1回だけ再祝福が必要**(補間→無補間で境界1px級の差が出うる)。再祝福時は CLI `image` コマンドで前後の出力を並べて目視確認し、以降を新基準とする。ベンチ比較を記録 |
| リスク | bild は正角度=時計回り、imaging.RotateNN は反時計回り。**規約変換はこのフェーズ唯一の危険点**であり、P0 の8向き網羅テストで機械的に検証する |
| 工数 | 半日 |

### P2. フル解像度物理回転の1回化(exif_rotation と crop の回転合成)

| | |
|---|---|
| 変更ファイル | `exif_rotation/proc.go`、`crop/proc.go`、`model/imgmeta.go`(フィールド1つ追加) |
| 内容 | `exif_rotation` は物理回転をやめ、①正規化に必要な直交演算(D4の元)を `meta.PendingExifOp`(新フィールド)に記録、②`ImageOrientation`(縦横判定)を**回転後の寸法計算**で従来通り設定、③被写体点変換は現行ヘルパーをそのまま使用。`crop` は冒頭で `PendingExifOp` と表示向き補正角を**D4合成表で1つの演算に合成**して1回だけ適用し、`PendingExifOp` を消費済みにする。以降のクロップ・リサイズ・`RequiredCorrectionAngle` の意味は不変 |
| 理由 | フル解像度の物理パスが最大3回→**常に1回以下**になる。両プロセッサは全呼び出し元で隣接しているため間に挟まる処理はなく、外部から見た事後条件(「crop通過後は設置向き・表示寸法」)は変わらない |
| 理解可能性の担保 | D4合成は8×8の明示的なテーブル+単体テストとして書く(条件分岐の入れ子にしない)。`exif_rotation` の責務は「物理回転する」から「必要な演算を宣言する」に変わるため、両ファイル冒頭のコメントで契約を書き直す。**このフェーズだけは責務の記述が変わる**ので、P1 と別コミットにし、差分レビューを独立させる |
| 検証 | P0/P1 のゴールデンが**無変更で** green のこと(直交演算の合成は結合的なので出力は P1 とピクセル一致するはず。一致しなければ合成表のバグ) |
| 工数 | 1日 |
| 備考 | P1 完了後に効果を再計測し、リサイズが律速で回転が誤差になっていれば**このフェーズは見送ってよい**(改修量最小の原則)。実施判断はベンチ数値で行う |

### P3. timestamp の全面回転の廃止(任意・小粒)

| | |
|---|---|
| 変更ファイル | `timestamp/proc.go` |
| 内容 | 「画像全体を逆回転→日付描画→再回転」(表示解像度2パス)をやめ、74×15pxの日付バッジを小さなキャンバスに描画し、バッジ側を `RequiredCorrectionAngle` 分回転して正しい隅に合成する |

| 工数 | 数時間 |

### P4. リサイズフィルタの選定(計測駆動)

| | |
|---|---|
| 変更ファイル | `crop/proc.go`(`resize()` 1関数) |
| 内容 | `imgconv.Resize`(Lanczos固定)を `imaging.Resize(img, W, H, <filter>)` の直接呼び出しに置き換え、フィルタを選定する。候補: `CatmullRom`(推奨初手)/`Linear`。判定手順: ①ベンチで差を測る ②CLI `image` コマンドで Lanczos との出力を各ディスプレイモデルのディザ設定込みで生成 ③**実機の電子ペーパーで目視比較**(PC画面での比較はディザ前提の本用途では判断を誤る) |
| 理由 | 直後に6〜7色への減色が入るため、Lanczos と CatmullRom の差はパネル上でほぼ確実に不可視。一方でリサイズは P1/P2 適用後に残る最大のコスト。ただし「見た目が変わりうる」唯一のフェーズなので、実機確認を通過した場合のみ採用する |
| 検証 | ゴールデンはフィルタ変更時のみ再祝福。ベンチ前後値を記録 |
| 工数 | 数時間(実機確認込み) |

## 5. 参考: EXIF向き ↔ 直交演算 対応表(P1 でコメントとして埋め込む)

| EXIF | 意味 | 現行実装(bild) | 置換後(imaging) |
|---|---|---|---|
| 1 | 正位置 | なし | なし |
| 2 | 左右反転 | FlipH | FlipH |
| 3 | 180° | Rotate(180) | Rotate180 |
| 4 | 上下反転 | FlipV | FlipV |
| 5 | 主対角転置 | Rotate(90)+FlipH(2パス) | **Transpose(1パス)** |
| 6 | 90°時計回り | Rotate(90) | **Rotate270**(imaging は反時計回り正) |
| 7 | 副対角転置 | Rotate(-90)+FlipH(2パス) | **Transverse(1パス)** |
| 8 | 90°反時計回り | Rotate(-90) | **Rotate90** |

crop 内: 現行 `-90°`(bild, 時計回り正)→ `imaging.Rotate90`、`+90°` → `imaging.Rotate270`。

## 6. 非スコープ

- HEIC/JPEG デコード自体の高速化(別課題。パイプライン合計では最大コストの可能性があるが本改修の目的外)
- スキャン時のサムネイル生成経路
- ディザ・減色アルゴリズム、エンコーダ
- `ImgMeta` の命名整理、プロセッサインターフェースへのエラー戻り値追加(長期レビュー 2-6 系の別件)

## 7. 想定効果とまとめ

- P1 だけで、全回転パスがピクセル毎三角関数の一般経路から添字並べ替えに変わる(パス単価で桁改善の見込み。確定値は P0 ベンチで取得)。加えて EXIF 5/7 と timestamp の**パス数自体が減り**、減色後画像の補間劣化という品質バグも消える
- P2 でフル解像度の物理回転が構造的に最大1回になり、「EXIF理解に追いつくために足した回転」の重複が設計として解消される
- P4 は残る最大コスト(リサイズ)への計測駆動の一手で、実機目視を合格条件とする
- どのフェーズも `exif_rotation → crop → filters → color_reduction → post` という現行の段階構造・メタデータ契約を変えないため、読み手のメンタルモデルは従来のまま通用する
